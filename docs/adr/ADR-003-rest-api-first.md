# ADR-003: Use an API-First REST Architecture

**Status:** Accepted  
**Date:** 2026-08-03  
**Decision Owner:** FlowCore Architecture

---

# Context

FlowCore provides functionality through multiple clients and external integrations.

Current and future consumers include:

- Web Application;
- Public Forms;
- Telegram Worker;
- External Integrations;
- Internal Administration Tools;
- Mobile Applications;
- Third-Party Systems.

The platform requires a stable and well-defined communication contract between clients and the backend.

The API must support:

- authentication;
- authorization;
- request validation;
- versioning;
- consistent error handling;
- pagination;
- filtering;
- sorting;
- OpenAPI documentation;
- automated testing.

---

# Decision

FlowCore follows an **API-First** approach.

The Backend API is the only public interface to the business logic.

All clients communicate with the backend exclusively through the REST API.

The initial API version is:

```text
/api/v1
```

FastAPI generates the OpenAPI specification and Swagger UI.

OpenAPI is considered the official contract between backend and clients.

The frontend must never access PostgreSQL, Redis, or internal services directly.

---

# API Design Rules

## Resource Naming

Resources use plural nouns.

Examples:

```text
/api/v1/organizations
/api/v1/projects
/api/v1/forms
/api/v1/submissions
```

---

## HTTP Methods

```text
GET     Retrieve resources

POST    Create resources

PATCH   Partially update resources

PUT     Replace resources

DELETE  Remove resources
```

---

## HTTP Status Codes

The API uses standard HTTP status codes.

Examples:

```text
200 OK

201 Created

204 No Content

400 Bad Request

401 Unauthorized

403 Forbidden

404 Not Found

409 Conflict

422 Validation Error

429 Too Many Requests

500 Internal Server Error
```

---

## Error Response Format

Every API error follows one structure.

Example:

```json
{
  "error": {
    "code": "organization_not_found",
    "message": "Organization was not found.",
    "details": [],
    "request_id": "9b8efb18-a9b0-4d69-9d94-6fb5fca6d0d2"
  }
}
```

---

## Pagination

Collection endpoints use pagination.

Example:

```text
GET /api/v1/projects?page=1&page_size=20
```

The maximum page size is limited.

---

## Filtering

Filtering is performed using query parameters.

Example:

```text
GET /api/v1/submissions?status=new
```

---

## Sorting

Sorting is also performed using query parameters.

Example:

```text
GET /api/v1/submissions?sort=-created_at
```

---

## Validation

All incoming requests are validated before business logic execution.

Validation includes:

- required fields;
- field formats;
- data types;
- value ranges;
- request structure.

Business rules remain inside the Domain layer.

---

# Authentication and Authorization

The API uses:

- JWT Access Tokens;
- Refresh Tokens;
- Role-Based Access Control (RBAC);
- Tenant-aware authorization.

Every protected request verifies:

- authenticated user;
- active session;
- organization membership;
- required permission;
- ownership of requested resources.

Resource identifiers alone never grant access.

---

# API Versioning

Breaking changes require a new API version.

Example:

```text
/api/v1
/api/v2
```

Non-breaking improvements may be added without changing the version.

Breaking changes include:

- removing fields;
- changing response structure;
- changing endpoint behavior;
- changing required request parameters.

---

# OpenAPI Rules

The generated documentation must include:

- endpoint summaries;
- endpoint descriptions;
- request schemas;
- response schemas;
- validation errors;
- authentication requirements;
- examples;
- module tags.

Swagger documentation is automatically generated by FastAPI.

---

# Consequences

## Positive

- Clear communication contract.
- Frontend and backend remain independent.
- Easy integration with third-party systems.
- Automatically generated documentation.
- Easier automated testing.
- Future mobile applications reuse the same API.
- API evolution is controlled through versioning.

## Negative

- API compatibility must be maintained.
- Documentation requires continuous updates.
- Poor endpoint design becomes difficult to change.
- Public APIs require strong security.

---

# Alternatives Considered

## GraphQL

Rejected because:

- REST fully satisfies current project requirements;
- REST is simpler to maintain;
- authorization is easier to implement;
- Swagger documentation is generated automatically.

GraphQL may be considered in future versions.

---

## gRPC

Rejected because:

- browser support is limited;
- external integrations primarily use REST;
- the project does not require high-performance service-to-service communication.

---

## Direct Database Access

Rejected because:

- it exposes infrastructure;
- bypasses authorization;
- increases security risks;
- tightly couples clients to the database schema.

---

## Server-Rendered Application

Rejected because FlowCore must support:

- Telegram;
- public APIs;
- external integrations;
- future mobile applications.

---

# Testing Requirements

The API must be covered by automated tests.

Mandatory test categories:

- successful requests;
- validation failures;
- authentication failures;
- authorization failures;
- tenant isolation;
- pagination;
- filtering;
- sorting;
- OpenAPI generation;
- error response format.

---

# Rules

- All clients use the REST API.
- Business logic is never implemented in the frontend.
- OpenAPI is the official API contract.
- Breaking changes require a new API version.
- Every endpoint must be documented.
- Every endpoint must validate input data.
- Authorization must be performed before business logic execution.

---

# Review Conditions

This decision should be reviewed if:

- GraphQL becomes a business requirement;
- multiple backend services require gRPC communication;
- API Gateway architecture is introduced;
- client requirements change significantly;
- REST no longer satisfies application needs.
